# 🚀 초보자를 위한 협업 문화 및 자동화 도구 도입 가이드 (Why DevOps & Linting?)

안녕하세요, 교육생 여러분! 신한DS 개척자 프로젝트에 합류하신 것을 진심으로 환영합니다. 

현업 프로젝트에 처음 진입하면 수많은 깃허브 액션(Actions), 린터(Linter) 스크립트, 엄격한 커밋 규칙 등을 마주하고 **"왜 이렇게 귀찮고 복잡한 설정들을 매번 지켜야 하지?"**라는 의문이 들 수 있습니다. 

이 문서는 여러분들이 **이 도구들의 핵심 가치(Why)를 스스로 납득하고 기쁘게 활용할 수 있도록 도우며, 이들이 없는 세상에서 개발자들이 어떤 끔찍한 고통을 겪는지** 일류 강사의 관점에서 아주 친절하게 설명해 드립니다. 차근차근 읽고 협업의 진짜 무기를 장착해 보세요! 🎓

---

## 📚 목차 (Pillars of DevOps)
* **Part 1. 코드 품질 및 협업 기본기 자동화**
  1. 코드 스타일 자동 정돈 (Spotless)
  2. API 문서 실시간 생성 (Swagger)
  3. 로컬 테스트 데이터 적재 (Data Seed)
  4. 메인 이력 정돈 병합 (Squash & Merge)
  5. 일관성 있는 깃 기록 (.gitmessage)
  6. 로컬 커밋 반려 방어막 (Lefthook)
* **Part 2. 데이터베이스 및 배포 안정성 자동화**
  7. DB 형상 제어 도구 (Flyway)
  8. 자바-DB 스키마 정합성 검증 테스트 (Hibernate Validate)
  9. Flyway 파일명 오타 린터 (Naming Linter)
  10. 운영 서버 무중단 DDL 검사기 (Online DDL Linter)
  11. 데이터 적재 시 마이그레이션 호환성 테스트 (Data Compatibility Test)
  12. 지속적 빌드 및 리소스 제어 (CI & Concurrency)

## Part 1. 코드 품질 및 협업 기본기 자동화

### 1. 🎨 코드 스타일 자동 정돈 (Spotless & Google Java Format)
*   **🛠️ 도입된 도구:** Gradle Spotless Plugin + Google Java Format
*   **❓ 왜 도입했나요?**
    개발자마다 코드를 작성하는 스타일(들여쓰기 너비, 중괄호 위치, 줄바꿈 빈도 등)이 모두 다릅니다. 이 도구는 소스 코드를 **구글 표준 자바 스타일 규격에 맞춰 명령 한 번으로 강제 정렬**해 줍니다.
*   **🚨 도입하지 않으면 어떤 참사가 발생하나요?**
    코드 리뷰를 진행할 때 실제 핵심 로직 대신 *"여기는 탭 대신 스페이스바를 2번 더 누르셨네요"*, *"중괄호는 다음 줄에 적어주세요"* 같은 **무의미한 스타일 지적질로 리뷰 게시판이 도배**됩니다. 또한 깃(Git) 변경 이력에 스타일만 바뀐 쓸데없는 Diff가 대량 발생하여 실제 어떤 비즈니스 로직이 바뀌었는지 추적하기가 불가능해집니다.
*   **💡 한 줄 요약:** 띄어쓰기와 들여쓰기는 기계에게 맡기고, 사람은 비즈니스 로직 설계에만 집중합시다!

---

### 2. 🔌 API 문서 실시간 생성 (Swagger / Springdoc OpenAPI)
*   **🛠️ 도입된 도구:** Springdoc OpenAPI
*   **❓ 왜 도입했나요?**
    자바 코드 상의 `@Tag`, `@Operation` 등 간단한 어노테이션 명세만으로 백엔드 API 명세서 웹페이지(`http://localhost:8080/swagger-ui/index.html`)를 실시간으로 자동 렌더링하고 직접 시뮬레이션해 볼 수 있습니다.
*   **🚨 도입하지 않으면 어떤 참사가 발생하나요?**
    별도의 엑셀이나 노션 페이지에 API 문서(URL, Request/Response body)를 수동으로 적어 관리해야 합니다. 백엔드 코드가 수정될 때 노션 문서를 깜빡하고 업데이트하지 않는 순간, **프론트엔드 개발자는 구식 문서를 보고 개발하다가 통신 에러를 겪고 백엔드 개발자 방을 찾아와 따지는 악순환**이 매일 반복됩니다.
*   **💡 한 줄 요약:** API 문서의 유일한 진실의 원천(Single Source of Truth)은 자바 코드 자체여야 합니다!

---

### 3. 💾 로컬 테스트 데이터 적재 (Data Seeding)
*   **🛠️ 도입된 도구:** Spring Boot `CommandLineRunner` + 환경 변수 격리
*   **❓ 왜 도입했나요?**
    로컬에서 서버를 처음 구동할 때 데이터베이스가 텅 비어있으면 로그인, 주문, 조회 등의 기능을 테스트하기 어렵습니다. 이 도구는 로컬 구동 시 암호화된 가상의 화주, 배송원, 지갑 잔액 등의 **더미 데이터들을 자동으로 안전하게 채워넣어 줍니다.**
*   **🚨 도입하지 않으면 어떤 참사가 발생하나요?**
    코드를 고친 뒤 작동 여부를 확인하기 위해 **매번 회원가입 API를 호출하고, DB 툴을 열어 포인트를 수동으로 충전하는 짓을 개발 서버를 켤 때마다 반복**해야 합니다. 테스트 데이터 세팅에만 하루 코딩 시간의 20%를 허비하게 됩니다.
*   **💡 한 줄 요약:** 서버를 키자마자 곧바로 테스트에 임할 수 있게 풍부한 기본 데이터를 세팅해 줍니다!

---

### 4. 🔀 메인 이력 정돈 병합 (Git Flow & Squash and Merge)
*   **🛠️ 도입된 약속:** 깃허브 설정 고정 및 PR 규칙 통제
*   **❓ 왜 도입했나요?**
    협업 시 메인 브랜치의 Git 기록(Commit Log)을 매우 단순하고 직관적으로 유지하기 위함입니다. PR 내에 쌓여 있는 자질구레한 커밋들(예: 오타 수정, 포맷 수정 등)을 병합되는 순간 **단 1개의 깨끗한 커밋으로 묶어서(Squash) 병합**합니다.
*   **🚨 도입하지 않으면 어떤 참사가 발생하나요?**
    메인 브랜치 히스토리를 켰을 때 수십 명의 개발자가 각자 올린 *"앗 오타 수정"*, *"진짜 진짜 최종 수정"*, *"커밋 템플릿 테스트"* 같은 **쓰레기성 이력들이 메인 히스토리 전체를 지배**하게 되어, 나중에 장애가 터졌을 때 "어떤 기능 PR에서 에러가 유입되었는지" 역추적하기가 불가능해집니다.
*   **💡 한 줄 요약:** 로컬에서는 자유롭게 많이 커밋하고, 합칠 때는 하나의 완전한 기능 단위 커밋으로 예쁘게 압축합시다!

---

### 5. ✉️ 일관성 있는 깃 기록 (Commit Message Template)
*   **🛠️ 도입된 도구:** `.gitmessage` 로컬 연동
*   **❓ 왜 도입했나요?**
    동료들이 작성한 커밋 메시지 내용만 보고도 "이 커밋이 무엇을 하고자 한 것인지" 단번에 파악하기 위해, 커밋 명령어 실행 시 약속된 규칙 힌트를 띄워주는 서식지 가이드라인입니다.
*   **🚨 도입하지 않으면 어떤 참사가 발생하나요?**
    커밋 로그가 `수정`, `test`, `Member.java`처럼 아무 정보도 없는 불친절한 텍스트로 가득 차게 됩니다. 동료가 짠 코드를 분석해야 하거나 에러를 역추적해야 할 때, 커밋 메시지만으로는 알 수 없어 수십 개의 소스 파일 디프(Diff)를 매번 눈으로 대조해야 하는 중노동이 수반됩니다.
*   **💡 한 줄 요약:** 커밋의 헤더 태그(`feat:`, `fix:`) 규칙은 동료 개발자에게 보내는 친절한 안내장입니다!

---

### 6. 🛡️ 로컬 커밋 반려 방어막 (Lefthook Git Hook Manager)
*   **🛠️ 도입된 도구:** Lefthook configuration (`lefthook.yml`)
*   **❓ 왜 도입했나요?**
    개발자가 자바 파일을 수정한 뒤 깃에 커밋(`git commit`)하려는 바로 그 찰나에, **백그라운드에서 코드 스타일(Spotless)과 규칙(파일명 등)을 컴퓨터가 사전에 즉시 확인**해 주는 로컬 자동화 훅입니다.
*   **🚨 도입하지 않으면 어떤 참사가 발생하나요?**
    포맷팅 검사를 깜빡 잊고 열심히 PR을 올린 뒤 빌드가 돌기를 3~5분 동안 기다립니다. 그리고 깃허브 액션 CI가 빨간 엑스박스(`spotlessCheck Fail`)를 뿜으며 빌드를 반려시킵니다. 그러면 개발자는 다시 로컬에서 코드를 만지고, 포맷팅 명령을 실행하고, 커밋해서 푸시한 뒤 또다시 깃허브 빌드를 기다려야 하는 **끝없는 대기/수정 뺑뺑이 루프**에 빠지게 됩니다.
*   **💡 한 줄 요약:** 잘못된 형식의 코드는 로컬에서 아예 커밋조차 안 되도록 막아주어, 대기 시간을 획기적으로 차단해 줍니다!

## Part 2. 데이터베이스 및 배포 안정성 자동화

### 7. 🗄️ DB 형상 제어 도구 (Flyway Database Migration)
*   **🛠️ 도입된 도구:** Flyway + JPA Buddy Integration
*   **❓ 왜 도입했나요?**
    데이터베이스 스키마(테이블 생성, 컬럼 추가/삭제 등)의 모든 변경 이력을 순차적인 SQL 파일(`V1__`, `V2__`)로 남겨 소스 코드와 마찬가지로 버전 관리를 수행합니다.
*   **🚨 도입하지 않으면 어떤 참사가 발생하나요?**
    팀 프로젝트 카카오톡 방에 *"주문 테이블에 컬럼 추가했으니 다들 로컬 DB에 이 SQL 복사해서 실행하세요!"*라고 전파해야 합니다. 이를 확인하지 못한 동료는 서버가 켜지지 않거나 조회가 실패해 반나절 동안 에러를 겪게 됩니다. 또한 실서버 배포 시점에 누군가 수동으로 DB 쿼리를 입력하는 과정에서 컬럼명 오타를 내 운영 DB가 깨지는 대형 참사가 발생할 수 있습니다.
*   **💡 한 줄 요약:** 데이터베이스의 역사(History) 역시 깃과 마찬가지로 코드로 이력을 투명하게 남기고 자동 동기화해야 합니다!

---

### 8. 🤝 자바-DB 스키마 정합성 검증 테스트 (Hibernate Schema Validation)
*   **🛠️ 도입된 도구:** `spring.jpa.properties.hibernate.ddl-auto=validate` 기반 단위 테스트
*   **❓ 왜 도입했나요?**
    자바 Entity 클래스에 설정한 매핑 정보(테이블명, 컬럼명, Null 허용 여부 등)가 Flyway가 생성해 둔 데이터베이스 물리 테이블 구조와 **100% 한 치의 오차도 없이 완벽하게 일치하는지** 스프링 부트를 띄워 검증합니다.
*   **🚨 도입하지 않으면 어떤 참사가 발생하나요?**
    자바 엔티티에는 `@Column(name = "member_id")`라고 적고, Flyway SQL 파일에는 `user_id`라고 테이블을 만들어 둡니다. 코드 빌드와 단위 테스트는 모킹(Mock) 때문에 정상 통과하지만, **실제 서버를 띄워 로그인 기능을 실행해 데이터를 DB에 적재하려는 순간 'Unknown column' 런타임 SQL 예외를 뿜으며 장애**를 일으키게 됩니다.
*   **💡 한 줄 요약:** 자바의 언어 설계 명세와 실제 MariaDB의 물리적 그릇 규격이 한 쌍으로 딱 맞아떨어지는지 대조해 줍니다!

### 9. 📐 Flyway 파일명 오타 린터 (Flyway Naming Linter)
*   **🛠️ 도입된 도구:** `scripts/lint-flyway-filenames.sh` 쉘 스크립트
*   **❓ 왜 도입했나요?**
    Flyway는 파일 이름 매핑 규칙이 매우 엄격합니다. 버전 접두사는 대문자 `V`여야 하며, 버전 번호와 설명 사이에는 **반드시 언더바 2개(`__`)**가 들어가야 합니다. 이 규칙이 파일명 상에서 제대로 지켜졌는지 정적으로 검사합니다.
*   **🚨 도입하지 않으면 어떤 참사가 발생하나요?**
    교육생이 실수로 `V1_init.sql`(언더바 1개) 또는 `v1__init.sql`(소문자 v)로 이름을 적습니다. Flyway는 규칙에 맞지 않는 파일을 마이그레이션 파일로 **인식조차 하지 않고 그냥 무시(Skip)**해 버립니다. 결국 컬럼 추가 코드가 운영 서버 DB에 반영되지 않아, 실제 사용자 거래 시 데이터 유실이나 쿼리 에러 장애가 터지고 만신창이가 된 후에야 파일명에 언더바가 부족했다는 충격적인 사실을 깨닫게 됩니다.
*   **💡 한 줄 요약:** Flyway가 파일명 오타 때문에 쿼리 파일을 그냥 무시하고 지나치는 현상을 원천 방지합니다!

---

### 10. 🛑 운영 서버 무중단 DDL 검사기 (Online DDL Linter)
*   **🛠️ 도입된 도구:** `scripts/lint-flyway-ddl.sh` 세미콜론 분할 분석 쉘 스크립트
*   **❓ 왜 도입했나요?**
    운영 중인 대용량 DB 테이블에 새로운 인덱스를 추가하거나 컬럼을 추가할 때 테이블 전체에 락(Table Lock)이 걸려 사용자가 서비스를 이용할 수 없는 상태에 빠집니다. 이를 방지하기 위해 **마이그레이션 쿼리에 무중단 옵션인 `ALGORITHM=INPLACE, LOCK=NONE`이 누락되었는지를 정밀 검사**합니다.
*   **🚨 도입하지 않으면 어떤 참사가 발생하나요?**
    회원 테이블의 이메일 조회 속도를 빠르게 하려고 가볍게 `CREATE INDEX` 쿼리 한 줄을 Flyway 파일에 추가해 배포합니다. 배포되는 순간 **회원 테이블 전체에 읽기/쓰기 락(Lock)이 걸리며 실시간으로 작동 중이던 모든 배송원 앱과 화주 웹의 화면이 뱅글뱅글 돌며 서비스 중단 상태**가 되고, 개발팀 전체에 비상이 걸려 장애 복구 회의를 소집해야 합니다.
*   **💡 한 줄 요약:** 대용량 테이블 변경 시 기습적인 테이블 락 장애가 유입되지 않도록 안전 가드레일을 쳐줍니다!

### 11. 🧪 기존 데이터 마이그레이션 호환성 테스트 (Data Compatibility Test)
*   **🛠️ 도입된 도구:** `FlywayMigrationDataCompatibilityTest.java` (JUnit5 통합 테스트)
*   **❓ 왜 도입했나요?**
    실제 데이터(레코드)가 차 있는 테이블에 새로운 마이그레이션 변경 사항을 덮어씌웠을 때, 데이터 제약 조건 충돌로 실패가 일어나지 않는지 가상 환경에서 사전 시뮬레이션해 보는 정밀 검증 단위 테스트입니다.
*   **🚨 도입하지 않으면 어떤 참사가 발생하나요?**
    이미 수십만 명의 회원 데이터가 들어있는 `member` 테이블에 기본값(Default)을 설정하지 않은 채 `age INT NOT NULL` 컬럼을 추가합니다. 빈 DB에서는 테스트가 다 성공했지만, **운영 서버에 배포하는 순간 기존 회원의 age 값으로 무엇을 채워 넣어야 할지 몰라 DB 엔진이 에러를 내며 배포가 전면 중단**되고 DB 형상이 꼬여 롤백을 수행해야 합니다.
*   **💡 한 줄 요약:** 빈 냄비(Clean DB)뿐만 아니라, 이미 밥이 가득 차 있는 냄비(Data DB) 위에서도 마이그레이션이 잘 동작하는지 검증합니다!

### 12. ⚡ 지속적 빌드 및 리소스 제어 (CI & Concurrency Control)
*   **🛠️ 도입된 도구:** GitHub Actions 워크플로우 통합 제어
*   **❓ 왜 도입했나요?**
    제출된 PR이 언제나 즉시 배포 가능한 상태를 유지하는지 가상 클라우드에서 spotless와 build를 매번 돌려 검증합니다. 또한, 연속해서 커밋을 올리면 이전 쓸모없어진 빌드는 자동 취소(`cancel-in-progress: true`)하여 빌드 대기열 고갈과 무료 API 한도 초과 오류(Rate Limit)를 지능적으로 차단합니다.
*   **🚨 도입하지 않으면 어떤 참사가 발생하나요?**
    동일 PR에 코드를 5번 연달아 푸시하면 5개의 가상 빌드 머신이 동시에 돌아갑니다. 이로 인해 깃허브 Actions 무료 사용량 쿼터가 반나절 만에 고갈되어 더 이상 PR을 빌드할 수 없는 마비 상태가 됩니다. 또한, API 호출량이 겹쳐 AI 리뷰어가 rate limit 에러를 뿜으며 응답을 거부하게 됩니다.
*   **💡 한 줄 요약:** 낭비되는 컴퓨팅 리소스를 지능적으로 차단하여 원격 빌드 대기 시간을 최소화합니다!
