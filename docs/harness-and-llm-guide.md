# 🔰 초보자와 LLM 사용자를 위한 테스트 하네스 & 피드백 루프 가이드

이 문서는 **코딩을 처음 배우는 초보 개발자**와 **AI(LLM) 코딩 도구를 처음 사용하는 분들**이 프로젝트의 품질을 높이고 안전하게 개발할 수 있도록 **테스트 하네스(Test Harness)**와 **피드백 루프(Feedback Loop)**의 개념 및 활용법을 아주 쉽게 설명합니다.

---

## 💡 1. 3분 만에 이해하는 핵심 개념

### 🏗️ 1) 테스트 하네스 (Test Harness) 란?
* **쉽게 비유하자면:** 신차를 도로에 내보내기 전에 시뮬레이션 장치에 차를 고정하고, 안전벨트와 각종 센서를 달아 충돌/가속/브레이크를 자동으로 시험해 보는 **'자동차 종합 시뮬레이터'**입니다.
* **프로젝트에서의 의미:** 우리가 만든 코드를 무작정 서버에 올리기 전에, **버튼 하나로 코드 규칙, DB 규격, 포맷팅, 비즈니스 로직을 한 번에 안전하게 검사해 주는 자동화 검사 장치**입니다.
* **왜 쓰는가 (WHY):** AI나 사람이 코드를 작성할 때 실수로 기존 기능을 망가뜨리거나 잘못된 코드를 올리는 사고(서버 장애)를 미리 방지하기 위해 안전 울타리로 사용합니다.
* **우리 프로젝트의 하네스:** 터미널에서 실행하는 `./scripts/verify.sh` 스크립트!

### 🔄 2) 피드백 루프 (Feedback Loop) 란?
* **쉽게 비유하자면:** 시험 문제를 풀고 $\rightarrow$ 정답지로 즉시 채점한 뒤 $\rightarrow$ 틀린 문제의 해설을 보고 스스로 다시 풀어보는 **'오답 노트 및 복습 과정'**입니다.
* **왜 쓰는가 (WHY):** 사람이 직접 수백 줄의 에러 로그를 읽고 고민할 필요 없이, 하네스가 수집한 에러를 AI에게 넘겨 **AI가 수초 만에 스스로 버그를 고치게(자가 치유) 하기 위해** 사용합니다.
* **프로젝트에서의 의미:** 
  1. 코드 작성/수정
  2. 하네스 실행 (`./scripts/verify.sh`)
  3. 에러 발생 시 로그(피드백) 확인
  4. 문제 원인 수정 후 다시 실행 (성공할 때까지 순환!)

## 🤖 2. LLM (AI 코딩 에이전트) 이용자를 위한 필수 지침

ChatGPT, Claude, Cursor, Antigravity 같은 **LLM AI 도구를 처음 사용할 때 많은 초보자들이 범하는 실수**가 있습니다.

### ❌ 초보자의 자주 하는 실수
> *"AI가 코드를 짜줬으니까 당연히 정답이겠지? 바로 Git에 커밋하고 푸시하자!"*

**현실은?** AI도 환각(Hallucination) 현상이 있거나, 프로젝트의 특수한 아키텍처 규칙을 깜빡하고 틀린 코드를 만들 때가 많습니다.

### ✅ 가장 똑똑하게 LLM을 활용하는 방법: "AI 하네스 피드백 루프"

AI에게 일시키는 올바른 4단계 순서:

```
[1단계] AI에게 원하는 기능 구현 요청
   │
   ▼
[2단계] 로컬 터미널에서 ./scripts/verify.sh 구동 (하네스 실행)
   │
   ├── ▶ [성공 (Exit 0)] ───▶ 안전하게 커밋! 🎉
   │
   └── ▶ [실패 (Error)] ───▶ [3단계] 터미널의 에러 로그를 복사해 AI에게 전달!
                                "방금 작성한 코드에서 이런 에러가 났어. 고쳐줘!"
                                   │
                                   ▼
                             [4단계] AI 수정 후 다시 ./scripts/verify.sh 실행 (루프 반복)
```

> 💡 **핵심:** 사람이 에러 원인을 하나하나 다 읽고 고민할 필요 없이, **검사 도구(하네스)가 뽑아준 에러 메시지를 AI에게 전달하기만 하면 AI가 스스로 에러를 고칩니다(자가 치유)!**

## 🚀 3. 우리 프로젝트의 4단계 하네스 검사 항목

터미널에서 `./scripts/verify.sh`를 구동하면 아래 4가지 항목이 순서대로 자동 검사됩니다.

| 단계 | 검사 항목 | 실패 시 의미 | 해결 방법 |
| :--- | :--- | :--- | :--- |
| **📌 1/4** | **Flyway 마이그레이션 파일명 규격** | SQL 파일 이름 규칙 위반 (예: `v1_` 소문자 작성 등) | `src/main/resources/db/migration/` 내 파일명 수정 |
| **📌 2/4** | **Flyway DDL 규격 (Online DDL)** | 무중단 배포를 위반하는 위험한 SQL 문법 포함 | DDL 스크립트 수정 (docs/flyway-guide.md 참고) |
| **📌 3/4** | **Spotless 코드 포맷팅 스타일** | 들여쓰기, 불필요한 import 등 스타일 규칙 불일치 | 터미널에 `./gradlew spotlessApply` 입력 |
| **📌 4/4** | **Gradle 테스트 및 ArchUnit 검사** | 기존 기능이 깨졌거나, 계층 구조 규칙 위반 | 에러 로그를 AI에게 전달하여 로직/의존성 수정 |

## 🛠️ 4. 자주 발생하는 에러와 대처법 (초보자 튜토리얼)

### Q1. 3단계 `Spotless`에서 검사가 실패해요!
* **원인:** 자바 코드의 띄어쓰기, 줄바꿈이 프로젝트 표준 규칙과 다를 때 발생합니다.
* **해결법:** 당황하지 말고 터미널에 아래 명령어를 입력하면 자동으로 코드가 예쁘게 정돈됩니다!
  ```bash
  ./gradlew spotlessApply
  ```

### Q2. 4단계 `ArchUnitTest`에서 검사가 실패해요!
* **원인:** 프로젝트의 아키텍처 규칙을 위반한 경우입니다. (예: `Controller`에서 `Repository`를 직접 불러서 사용한 경우)
* **해결법:** `Controller`는 반드시 `Service`를 통해서만 데이터에 접근해야 합니다. AI에게 *"Controller가 Repository를 직접 참조하지 않고 Service를 거치도록 리팩토링해 줘"* 라고 요청하세요.

### Q3. 4단계 단위/통합 테스트에서 검사가 실패해요!
* **원인:** 코드를 수정하면서 기존에 잘 동작하던 다른 기능이 깨졌거나 비즈니스 로직에 오류가 있는 경우입니다.
* **해결법:** 터미널에 빨간색으로 출력된 에러 메시지와 `Caused by:` 라인을 복사하여 AI에게 전달하세요.

## ⚡ 5. 초보자를 위한 원클릭 자동 PR 명령어 (`./pr`)

복잡한 Git 명령어나 테스트 스크립트를 하나하나 외울 필요 없이, 터미널에 **`./pr`** 단 한 줄만 입력하면 모든 과정이 자동으로 완료됩니다.

```bash
./pr
```

### 🤔 ❓ "근데 앞에 `./`는 왜 붙이는 건가요?"
* **`.` (점 하나)**: "현재 내가 위치한 이 폴더"라는 뜻입니다.
* **`/` (슬래시)**: "~폴더 안에 있는"이라는 구분자입니다.
* **`./pr`**: **"시스템 전체에서 찾지 말고, [현재 이 폴더 안에 있는] `pr`이라는 자동화 실행 파일을 구동해 줘!"**라는 컴퓨터와의약속입니다.

---

### 🔄 `./pr` 단 한 줄을 치면 내부에서 일어나는 일

1. **자동 검증 실행:** `./scripts/verify.sh` 하네스를 실행하여 린트, 코드 포맷팅, 아키텍처 규칙, 전체 테스트를 1초 만에 검사합니다.
2. **자동 커밋 & 푸시:** 검증을 모두 통과하면 변경된 코드를 깔끔하게 `git commit` 및 Remote 레포지토리로 `git push`합니다.
3. **자동 PR 생성:** GitHub CLI(`gh`)를 통해 PR을 작성하고 웹 링크를 터미널 화면에 즉시 출력해 줍니다.

---

## 📝 6. 요약: 초보 개발자의 하루 꿀팁

1. 작업 시작 전 `git pull`을 받습니다.
2. AI의 도움을 받아 기능을 구현합니다.
3. **작업을 마친 후 터미널에 `./pr` 단 한 줄만 입력합니다.**
4. 혹시 에러가 발생하면 에러 로그를 AI에게 복사해 보여주고 *"에러 고쳐줘"* 라고 하면 끝!
