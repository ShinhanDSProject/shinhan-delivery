## 📌 1. 배경 및 문제 제기 (Context & Problem Statement)

`main`의 "37개 HTML 페이지 Thymeleaf SSR 전환" 작업(#261)을 점검한 결과, `HomeWebController`가 `Model`에 데이터를 채워도 `home.html` 템플릿에는 `th:` 바인딩이 전혀 없고, 실제 화면 데이터(회원 이름, 진행 중인 배송, 알림)는 여전히 `<script>`의 `fetch()`가 클라이언트에서 그리는 CSR 방식이었다. 원인은 ADR-0001에서 채택한 인증 방식에 있다 — 로그인 시 발급된 JWT를 `localStorage`에 저장하고 `Authorization` 헤더로만 API에 실어 보내는 순수 SPA 패턴이라, 브라우저가 SSR 페이지(`/home`)에 직접 접속하면 서버는 렌더링 시점에 "누가 요청했는지" 전혀 알 수 없다. `home.html`을 시작으로 나머지 페이지들도 실제 SSR로 전환하려면 이 문제를 먼저 풀어야 한다.

`home.html`을 레퍼런스로 전환을 마친 뒤, 이 ADR의 적용 범위는 `home.html` 한 페이지가 아니라 **같은 문제를 가진 나머지 WebController 전체(`AddressWebController`, `CategoryWebController`, `CommonWebController`, `CourierWebController`, `DeliveryWebController`, `MemberWebController`, `NoticeWebController`, `NotificationWebController`, `PaymentWebController`, `RealtimeWebController`)로 순차 확장하는 것**으로 확정되었다. 이에 따라 SSR 페이지에서 사용자가 수행하는 상태 변경 액션(폼 제출, 버튼 클릭)까지 서버로 직접 처리할지 여부도 함께 결정해야 했다.

## 💡 2. 비교 및 검토된 대안들 (Alternatives Considered)

### Option 1: 인증 구조는 그대로 두고 비인증 데이터만 SSR
* **동작 방식:** 카테고리 목록처럼 회원과 무관한 공용 데이터만 서버에서 렌더링하고, 회원별 데이터(배송현황, 알림 등)는 지금처럼 JS `fetch()`로 유지.
* **장점:** 인증 구조를 전혀 건드리지 않아 리스크와 작업량이 가장 작음.
* **단점:** 홈 화면에서 실제로 사용자에게 보여지는 핵심 데이터가 전부 회원별 개인화 데이터라, 이 방식으로는 SSR 전환 효과가 사실상 없음. 새로고침 시 로딩 깜빡임 문제도 해결되지 않음.

### Option 2: 세션/쿠키 기반 인증으로 전면 전환
* **동작 방식:** JWT 무상태 인증을 폐기하고 서버 세션 + 쿠키 기반 인증으로 되돌림.
* **장점:** SSR 페이지의 인증 처리가 프레임워크 표준 방식으로 단순해짐.
* **단점:** ADR-0001에서 채택한 무상태 확장성(Scale-out) 이점을 전부 포기해야 하고, 기존 REST API·모바일 클라이언트 인증 방식까지 전부 바꿔야 하는 과도한 변경 범위.

### Option 3: 기존 JWT 체계 유지 + 로그인 시 accessToken을 HttpOnly 쿠키로 병행 발급 - ⭐ [CHOSEN]
* **동작 방식:** 로그인 응답의 JSON 바디(`TokenResponse`)는 그대로 두고, `Set-Cookie`로 `accessToken`을 HttpOnly 쿠키로도 함께 내려준다. `JwtAuthenticationFilter`는 `Authorization` 헤더가 없고 요청 경로가 `/api/`로 시작하지 않을 때만 쿠키에서 토큰을 읽어 인증한다. REST API(`/api/v1/**`)는 계속 헤더 전용으로만 인증한다.
* **장점:** ADR-0001의 무상태 JWT 구조와 서버 확장성을 그대로 유지하면서, 기존 REST API·모바일 클라이언트·아직 전환 안 된 CSR 페이지에는 영향이 전혀 없음. SSR 페이지만 추가로 로그인 사용자를 식별할 수 있게 됨.
* **단점 및 보완책:**
  - 이 프로젝트는 CSRF 방어가 꺼져 있어(`SecurityConfig`의 `csrf().disable()`), 쿠키 인증을 상태 변경 API까지 허용하면 새로운 CSRF 노출면이 생김 ➔ **쿠키 폴백을 `/api/**` 경로에서는 명시적으로 제외**해 SSR GET 렌더링에만 범위를 한정.
  - HttpOnly 쿠키는 JS로 지울 수 없어 로그아웃이 불완전해질 수 있음 ➔ **`POST /api/v1/members/logout` 엔드포인트를 추가**해 쿠키를 `Max-Age=0`으로 즉시 만료시키고, 클라이언트 로그아웃 로직이 이 엔드포인트를 먼저 호출하도록 함.

### Option 4: SSR 페이지의 상태 변경 액션도 `th:action` 네이티브 폼 POST로 서버에 직접 제출
* **동작 방식:** 배송 신청·결제·PIN 설정·프로필 수정 등 지금 JS `fetch()`로 처리하는 액션들을 Thymeleaf `th:action` 폼 제출로 바꿔 서버가 직접 처리하고 리다이렉트/플래시 메시지로 결과를 보여줌.
* **장점:** "화면 진입은 물론 액션 처리까지" 전통적인 서버 렌더링 방식으로 통일되어 개념적으로 더 단순해 보임.
* **단점:**
  - 브라우저는 폼 제출 시 `accessToken` 쿠키를 자동으로 실어 보내므로, Option 3에서 "쿠키는 SSR GET 렌더링에만 쓴다"고 그은 선을 벗어나 CSRF 방어(`csrf().disable()`)를 다시 켜야 함 — Option 3에서 의도적으로 피한 위험을 재도입하게 됨.
  - CSRF를 켜면 `Authorization` 헤더 기반의 REST API 뮤테이션 호출과 폼 기반 뮤테이션이 뒤섞여, 기존 JS `fetch()` 호출 전체(템플릿 19곳)에도 CSRF 토큰 첨부 작업이 필요해짐.
  - 폼 제출은 풀 페이지 리로드를 유발해 인라인 유효성 검사·토스트 메시지 등 기존 UX를 리다이렉트+플래시 패턴으로 재설계해야 함.
  - 알림 뱃지 WebSocket 구독, 실시간 배송 위치 추적, 매칭 대기 폴링처럼 애초에 서버 폼 렌더링으로 대체 불가능한 실시간 기능은 어차피 JS로 남아, 이 방식을 택해도 "순수 SSR"이 완성되지 않음.
* 위 이유로 **채택하지 않음.**

## 🎯 3. 최종 의사결정 (Architectural Decision)

**Option 3 (JWT 쿠키 폴백 병행 발급)**을 SSR 페이지 인증의 표준 방식으로 채택한다.

### 🔒 적용 방침:
1. `JwtProvider`에 쿠키 `Max-Age` 계산용 `getAccessTokenExpirationSeconds()`를 추가한다.
2. `MemberController.login()`은 기존 JSON 응답을 유지한 채 `Set-Cookie`로 `accessToken`(HttpOnly, `SameSite=Lax`, `Path=/`, `Max-Age`=Access Token 만료시간과 동일)을 추가한다.
3. `MemberController.logout()`을 신규 추가해 동일한 쿠키를 `Max-Age=0`으로 즉시 만료시킨다.
4. `JwtAuthenticationFilter.resolveToken()`은 `Authorization` 헤더를 최우선으로 확인하고, 헤더가 없고 요청 경로가 `/api/`로 시작하지 않는 경우에만 쿠키를 폴백으로 확인한다. REST API 인증 방식은 변경하지 않는다.
5. 로컬 개발 환경(HTTP)을 고려해 쿠키의 `Secure` 속성은 현재 `false`로 설정한다 — 배포 환경(HTTPS) 적용 시 프로파일별로 `true`로 전환하는 후속 작업이 필요하다.
6. **적용 범위 및 액션 처리 방침:** 이 결정은 `home.html`뿐 아니라 나머지 10개 WebController에도 동일하게 적용되는 SSR 인증의 표준이다. 단, SSR 페이지의 상태 변경 액션(폼 제출, 버튼 클릭)은 계속 기존 REST API에 대한 JS `fetch()` 호출(`Authorization` 헤더 방식)로 처리하며, Thymeleaf `th:action`을 통한 서버 직접 폼 POST(Option 4)는 채택하지 않는다. 이에 따라 CSRF 보호도 지금처럼 비활성 상태를 유지한다 — `accessToken` 쿠키는 오직 SSR 페이지의 GET 렌더링 시 사용자 식별에만 쓰이고, 상태를 변경하는 어떤 요청에도 관여하지 않는다.

## 🟢 4. 예상되는 효과 및 결과 (Consequences)

* **긍정적 효과 (Positive):**
  - `home.html`처럼 회원별 데이터를 보여줘야 하는 SSR 페이지가 새로고침 시 깜빡임 없이 완성된 화면을 바로 렌더링할 수 있게 됨.
  - 기존 REST API, 모바일 클라이언트, 아직 전환하지 않은 CSR 페이지는 전혀 영향받지 않아 하위 호환성 100% 유지.
  - ADR-0001에서 확보한 무상태 확장성 이점을 그대로 보존.
* **트레이드오프 및 관리 요소 (Negative/Risks):**
  - `Secure=false`는 로컬 개발 편의를 위한 임시 설정으로, 배포 전 HTTPS 프로파일에서 `true`로 전환하지 않으면 쿠키가 평문 채널로 노출될 수 있음 — 기술 부채로 추적 필요.
  - 나머지 10개 WebController를 SSR로 전환할 때마다 각 컨트롤러가 `principal == null` 케이스(비로그인 접근)를 빠짐없이 처리해야 함 — `home.html` 전환에서 확립한 패턴(비로그인 시 `/login` 리다이렉트, PIN 미설정 시 `/payment-pin-settings` 리다이렉트)을 그대로 재사용한다.
  - 로그아웃 처리가 "서버 쿠키 만료 + 클라이언트 `localStorage` 삭제" 두 단계로 늘어나, 향후 인증 관련 변경 시 두 지점을 함께 고려해야 함.
  - Option 4를 채택하지 않기로 함에 따라, WebSocket 기반 알림·실시간 위치 추적 등 상호작용이 필요한 부분은 SSR 전환 완료 후에도 계속 JS로 남는다 — "화면 진입은 SSR, 액션과 실시간 갱신은 JS"인 하이브리드 구조가 이 프로젝트의 영구적인 표준이 된다는 점을 팀 전체가 인지하고 있어야 함.
