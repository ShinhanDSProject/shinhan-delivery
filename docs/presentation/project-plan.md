# Shinhan Delivery 프로젝트 기획서

## 1. 프로젝트 개요

### 1.1 프로젝트명
Shinhan Delivery

### 1.2 프로젝트 유형
실시간 배송 매칭 기반 포인트 결제형 온디맨드 배송 플랫폼

### 1.3 프로젝트 소개
Shinhan Delivery는 사용자가 앱에서 배송 요청을 생성하고, 배송원이 이를 수락하여 배송을 수행하며, 사용자는 앱 내 포인트를 통해 배송비를 결제하고 실시간으로 배송 상태를 확인할 수 있는 서비스입니다.

본 프로젝트는 단순 배송 요청 CRUD를 넘어서 다음과 같은 운영형 기능을 포함합니다.

- 역할 기반 회원 체계
- 배송원 장비 및 자격 관리
- 거리/무게/물품 크기 기반 배송비 계산
- 포인트 충전 및 포인트 결제
- 결제 PIN 기반 보안 검증
- 배송 요청 수락 경쟁 제어
- 배송 상태 실시간 브로드캐스트
- 고객 취소 시 환불 및 배송원 보상 처리
- 관리자 승인 및 운영 화면 제공

### 1.4 기획 배경
기존의 단순 심부름/배송 서비스는 요청 등록과 배정까지만 다루는 경우가 많고, 실제 서비스 운영에 필요한 다음 요소가 부족한 경우가 많습니다.

- 결제와 배송 요청 생성의 원자적 처리
- 중복 결제 방지
- 배송원 수락 충돌 방지
- 고객 취소에 대한 정산 정책
- 실시간 추적 및 운영 관리
- 배송원 자격 검수와 역할 분리

Shinhan Delivery는 이러한 문제를 반영하여, 실제 운영을 고려한 구조적 완성도를 갖춘 배송 플랫폼을 목표로 합니다.

### 1.5 프로젝트 목표
본 프로젝트의 목표는 다음과 같습니다.

1. 사용자가 배송 요청부터 결제, 상태 조회, 취소까지 하나의 앱 흐름 안에서 처리할 수 있도록 한다.
2. 배송원이 자신의 운송수단 조건에 맞는 배송 요청만 효율적으로 조회하고 수락할 수 있도록 한다.
3. 배송비 산정, 포인트 결제, 환불, 보상, 상태 전이 등 핵심 비즈니스 로직을 서버 중심으로 안전하게 처리한다.
4. 역할, 권한, 상태, 이력, 정산 등 실제 서비스 운영에서 중요한 요소를 구조적으로 반영한다.

## 2. 서비스 비전 및 핵심 가치

### 2.1 서비스 비전
“사용자와 배송원을 실시간으로 연결하고, 안전한 결제와 신뢰 가능한 배송 흐름을 제공하는 스마트 배송 플랫폼”

### 2.2 핵심 가치
- **간편성**: 사용자는 복잡한 절차 없이 배송을 요청하고 결제할 수 있다.
- **신뢰성**: 결제, 취소, 환불, 배송 완료 증빙이 명확하게 관리된다.
- **실시간성**: 배송 상태와 배송원 위치를 실시간으로 확인할 수 있다.
- **안전성**: 결제 PIN, 멱등 키, 락 기반 처리로 데이터 정합성을 확보한다.
- **운영성**: 배송원 승인, 알림, 공지, 관리자 대시보드 등 운영 기능을 포함한다.

## 3. 주요 이해관계자 및 사용자 정의

### 3.1 고객(Customer)
배송이 필요한 일반 사용자로, 배송 요청 생성과 결제의 주체이다.

주요 목적:
- 배송 요청 등록
- 배송비 사전 확인
- 포인트 충전 및 결제
- 배송 진행 현황 확인
- 배송 취소 및 내역 조회

### 3.2 배송원(Courier)
배송 요청을 수락하고 실제 배송을 수행하는 사용자이다.

주요 목적:
- 활동 가능한 장비 등록
- 승인 후 주문 수락
- 픽업/배송 완료 처리
- 증빙 사진 업로드
- 본인에게 배정된 주문 실시간 수행

### 3.3 관리자(Admin)
서비스 운영과 검수, 공지, 배송원 승인 등 관리 기능을 담당한다.

주요 목적:
- 배송원 승인/반려
- 운영 화면 확인
- 공지 노출
- 서비스 운영 정책 반영

## 5. 사용자 여정

## 5.1 고객 여정
1. 회원가입 후 로그인한다.
2. 포인트 지갑이 자동으로 생성된다.
3. 필요 시 결제 PIN을 등록한다.
4. 배송 요청 화면에서 출발지, 도착지, 물품 정보, 요청사항을 입력한다.
5. 시스템이 예상 배송비를 계산한다.
6. 사용자는 포인트를 충전하거나 기존 포인트를 사용해 결제한다.
7. 결제 성공 시 배송 요청이 등록된다.
8. 조건에 맞는 배송원에게 오퍼가 전송된다.
9. 배송원이 수락하면 배송이 시작된다.
10. 사용자는 배송 상태와 위치를 확인한다.
11. 배송 완료 후 증빙 사진과 내역을 확인한다.
12. 필요 시 배송 취소 또는 과거 요청 기반 재주문을 진행한다.

## 5.2 배송원 여정
1. 배송원 계정으로 회원가입한다.
2. 장비 및 자격 정보를 제출한다.
3. 승인 후 활성 상태가 되면 주변 요청을 조회할 수 있다.
4. 자신의 장비 조건에 맞는 요청을 수락한다.
5. 픽업 완료 후 사진을 등록한다.
6. 목적지에 도착해 배송 완료 처리와 증빙 사진을 등록한다.
7. 차량/장비는 다시 가용 상태로 복귀한다.

## 5.3 관리자 여정
1. 관리자 계정으로 로그인한다.
2. 대기 중인 배송원 승인 요청을 확인한다.
3. 증빙 자료를 검토해 승인 또는 반려한다.
4. 운영 현황, 공지, 사용자 흐름을 관리한다.

## 6. 기능 요구사항

## 6.1 회원 및 인증 기능

### 6.1.1 회원가입
- 이메일, 비밀번호, 이름, 연락처를 입력하여 가입한다.
- 사용자 역할은 고객 또는 배송원으로 구분된다.
- 이메일은 중복될 수 없다.
- 비밀번호는 암호화 후 저장한다.
- 배송원 가입 시 기본 장비 정보 또는 활동 조건을 함께 설정할 수 있다.
- 가입 직후 포인트 지갑이 자동 생성된다.
- 배송원 역할인 경우 자격 승인 상태를 관리한다.

### 6.1.2 로그인
- 이메일/비밀번호 조합으로 로그인한다.
- 성공 시 Access Token과 Refresh Token을 발급한다.
- 잘못된 비밀번호 입력 시 인증 실패 처리한다.

### 6.1.3 토큰 재발급
- Refresh Token 검증 후 새로운 토큰을 발급한다.
- 유효하지 않은 토큰은 재발급을 거부한다.

### 6.1.4 프로필 및 보안 관리
- 이름, 연락처, 활동 지역 등 기본 정보를 수정할 수 있다.
- 비밀번호 변경 시 현재 비밀번호 검증이 필요하다.
- 새 비밀번호와 확인 값이 일치해야 한다.
- 이전 비밀번호 재사용은 제한한다.
- 결제 PIN은 별도로 설정 및 변경할 수 있다.

## 6.2 배송 요청 기능

### 6.2.1 배송 요청 생성
- 고객은 출발지와 도착지 주소 및 좌표를 입력한다.
- 물품 무게와 크기를 입력한다.
- 배송 요청사항을 입력할 수 있다.
- 요청사항은 배송 방식에 따라 현관 비밀번호, 상세 위치, 메모, 참고 사진 등을 포함한다.
- 서버가 좌표를 기준으로 실제 거리와 배송비를 계산한다.
- 계산된 금액을 기준으로 결제 후 배송 요청이 생성된다.

### 6.2.2 예상 배송비 계산
- 배송 요청을 생성하지 않고도 예상 요금을 확인할 수 있다.
- 계산 기준은 실제 결제 시와 동일해야 한다.
- 클라이언트가 입력한 요금을 그대로 믿지 않고 서버가 최종 계산한다.

### 6.2.3 배송 요청 조회
- 고객은 본인의 배송 요청 목록을 페이징 형태로 조회할 수 있다.
- 상태별 필터링이 가능하다.
- 상세 조회 시 배송원 정보, 차량 종류, 매칭 시각 등을 확인할 수 있다.
- 고객 본인 또는 배정된 배송원만 상세를 조회할 수 있다.

### 6.2.4 배송 요청 수정 및 삭제
- 배송 요청은 `REQUESTED` 상태일 때만 수정 가능하다.
- 이미 수락되었거나 완료/취소된 배송은 수정할 수 없다.
- 매칭된 주문은 삭제할 수 없다.

### 6.2.5 재주문 초안
- 과거 배송 내역을 기반으로 새 요청 작성에 필요한 입력값을 다시 불러올 수 있다.

## 6.3 배송원 매칭 기능

### 6.3.1 주변 주문 조회
- 배송원은 자신의 현재 위치 또는 장비 위치를 기준으로 반경 내 배송 요청을 확인한다.
- 조회 대상은 `REQUESTED` 상태의 주문이다.
- 차량의 최대 적재 무게와 최대 이동 거리 조건을 만족하는 요청만 노출된다.
- 반경 내 주문은 픽업지와의 거리 순으로 정렬된다.

### 6.3.2 주문 수락
- 배송원만 주문을 수락할 수 있다.
- 동일 주문은 한 명의 배송원만 수락 가능하다.
- 동일 차량은 동시에 여러 주문을 수락할 수 없다.
- 주문 수락 시 배송 상태는 `MATCHED`로 변경된다.
- 매칭 정보가 생성되고 차량은 바쁜 상태로 전환된다.

### 6.3.3 수락 충돌 방지
- 동시에 여러 배송원이 같은 주문을 누를 수 있으므로, 주문 수락은 경쟁 조건을 고려해야 한다.
- 비관적 락 및 저장소 제약을 통해 한 명만 성공하도록 처리한다.

## 6.4 배송 수행 기능

### 6.4.1 픽업 처리
- 배정된 배송원만 픽업 완료 처리를 할 수 있다.
- 주문 상태가 `MATCHED`일 때만 픽업 완료가 가능하다.
- 픽업 완료 시 물품 확인 사진과 픽업 시각을 저장한다.
- 상태는 `PICKED_UP`로 전이된다.

### 6.4.2 배송 완료 처리
- 배정된 배송원만 완료 처리할 수 있다.
- 주문 상태가 `PICKED_UP`일 때만 완료 가능하다.
- 완료 시 증빙 사진과 완료 시각을 저장한다.
- 상태는 `COMPLETED`로 변경된다.
- 사용 중이던 차량은 다시 `AVAILABLE` 상태로 복귀한다.

### 6.4.3 사진 조회
- 픽업 사진과 완료 사진은 접근 권한이 있는 사용자만 조회할 수 있다.
- 사진이 등록되지 않은 경우 예외 처리한다.

## 6.5 결제 및 포인트 기능

### 6.5.1 포인트 지갑
- 회원마다 하나의 포인트 지갑을 가진다.
- 회원가입 시 자동으로 생성된다.
- 현재 잔액을 저장한다.

### 6.5.2 포인트 충전
- 사용자는 포인트를 충전할 수 있다.
- 충전 성공 시 잔액이 증가한다.
- 모든 충전은 이력에 기록된다.
- 동일 요청이 반복 전송되어도 한 번만 반영되도록 처리한다.

### 6.5.3 포인트 사용
- 배송 결제 시 포인트를 사용한다.
- 서버가 잔액을 직접 검증한다.
- 잔액이 부족하면 결제를 거부한다.
- 결제 성공 시 잔액을 차감하고 이력을 저장한다.

### 6.5.4 환불
- 배송 취소나 타임아웃 등 특정 상황에서 포인트를 환불한다.
- 환불 금액과 기준 사유를 함께 기록한다.
- 동일 환불이 반복 반영되지 않도록 참조 ID와 멱등 구조를 사용한다.

### 6.5.5 배송원 보상
- 고객 취소 등 특정 상황에서 배송원에게 보상 포인트를 적립할 수 있다.
- 보상 역시 포인트 이력으로 기록한다.

### 6.5.6 결제 PIN
- 결제 전 본인 인증 강화를 위해 PIN 검증을 사용할 수 있다.
- PIN은 해시로 저장한다.
- 실패 횟수를 기록하고 3회 이상 실패 시 잠금한다.

### 6.5.7 결제 멱등성
- 포인트 충전, 사용, 환불은 `Idempotency-Key`를 사용하여 중복 처리 방지한다.
- 같은 요청이 재전송되면 기존 결과를 반환한다.

## 6.6 취소 및 정산 기능

### 6.6.1 고객 취소
- 고객은 자신의 배송에 대해서만 취소를 요청할 수 있다.
- 취소 가능 상태는 `REQUESTED` 또는 `MATCHED`이다.
- 이미 완료되었거나 픽업된 주문은 일반 취소할 수 없다.

### 6.6.2 취소 정산 정책
- `REQUESTED` 상태 취소 시 전액 환불할 수 있다.
- `MATCHED` 상태 취소 시 취소 수수료가 발생할 수 있다.
- 현재 구현 기준 매칭 이후 취소 수수료는 최대 1000포인트 범위에서 반영된다.
- 취소 수수료는 배송원 이동 보상 개념으로 활용될 수 있다.

### 6.6.3 정산 처리
- 고객 환불과 배송원 보상은 하나의 취소 흐름 안에서 함께 처리한다.
- 배송 요청에는 취소 사유, 이전 상태, 수수료, 환불액, 보상액, 처리 시각을 남긴다.

### 6.6.4 자동 타임아웃
- 일정 시간 동안 매칭되지 않은 배송 요청은 자동 취소 대상이 될 수 있다.
- 자동 취소 시 환불 여부와 재시도 정보가 함께 기록된다.

## 8. 배송비 정책

### 8.1 계산 목적
배송비는 클라이언트에서 임의 입력된 값이 아니라, 서버가 기준 공식을 통해 계산해야 한다.  
이를 통해 요금 조작을 방지하고 요청 생성과 결제 흐름을 일치시킨다.

### 8.2 계산 방식
- 기본요금: 3000
- 거리 할증: km당 500
- 무게 할증: kg당 200
- 물품 크기 할증:
  - SMALL: 0%
  - MEDIUM: 30%
  - LARGE: 60%

### 8.3 계산 원칙
- 거리 계산은 출발지와 도착지 좌표를 기준으로 한다.
- 요청 생성과 예상 배송비 조회는 동일한 계산기를 사용한다.
- 최종 결제 금액은 서버 계산 결과를 기준으로 한다.

## 9. 상태 설계

## 9.1 배송 상태
- `REQUESTED`: 결제 완료 후 배송원 대기 상태
- `MATCHED`: 배송원이 수락한 상태
- `PICKED_UP`: 배송원이 물품을 인수한 상태
- `COMPLETED`: 배송이 종료된 상태
- `CANCELLED`: 고객 요청 또는 자동 타임아웃으로 취소된 상태

## 9.2 차량 상태
- `AVAILABLE`: 주문 수락 가능한 상태
- `BUSY` 또는 사용 중 상태: 배송 수행 중
- 그 외 승인/활성 여부가 별도 운영 상태에 영향을 줄 수 있음

## 9.3 포인트 이력 타입
- `CHARGE`
- `USE`
- `REFUND`
- `COURIER_COMPENSATION`

## 12. 운영 정책

### 12.1 배송원 승인 정책
- 배송원 역할은 가입 즉시 완전 승인되지 않을 수 있다.
- 자격 증빙 서류를 등록해야 한다.
- 관리자는 승인 또는 반려를 수행할 수 있다.
- 반려 후 재제출 시 재심사 가능 상태로 전환될 수 있다.

### 12.2 장비 운영 정책
- 장비는 승인 상태 및 활성 상태를 가진다.
- 장비 정보에는 차종, 적재 가능 무게, 이동 가능 거리, 사진 등 운영용 데이터가 포함된다.

### 12.3 취소 및 보상 정책
- 고객 취소 시 현재 상태에 따라 환불액이 달라질 수 있다.
- 배송원 보상이 필요한 경우 보상 포인트를 지급한다.
- 모든 정산 결과는 이력으로 남긴다.
